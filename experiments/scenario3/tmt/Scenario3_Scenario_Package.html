TB4 Backend Account Management Components ↔ Persistent User Database Storage The backend services (Account Management Service, Password Reset Token Module, User Profile API Handler) perform active processing logic; the database is a passive persistence layer. They operate in different trust contexts — processing logic is transient and rule-based, while storage is persistent and holds sensitive data at rest. · All database queries and updates cross this boundary (DF3, DF8, DF11, DF12).
· User credentials, profile data, and token records are stored at rest on the database side.
· Compromise of this boundary could expose all stored user data or allow unauthorized record modification.

8. Architecture Explanation

The Scenario 3 architecture models a web-based user account management application with a three-tier structure: a client-side presentation tier (Web Frontend Interface), a server-side application tier comprising three components (Account Management Service, Password Reset Token Module, and User Profile API Handler), and a data tier (Backend User Database). The system supports two primary workflows: password reset and authenticated profile management.

Component Interactions. The system is organized around two distinct functional domains. The password reset workflow involves the Web Frontend Interface, the Account Management Service, the Password Reset Token Module, the Backend User Database, and an External Communication Channel. When a user initiates a password reset (DF1), the frontend forwards the request to the Account Management Service (DF2), which verifies the user account against the database (DF3) and coordinates token generation through the Token Module (DF4). The generated token is delivered to the user through an external communication channel (DF5). The user then submits the token and a new password (DF6, DF7), which the Account Management Service validates and uses to update the stored password (DF8).

The profile management workflow involves the Web Frontend Interface, the User Profile API Handler, and the Backend User Database. Authenticated users submit API requests to retrieve or modify profile information (DF9). The frontend forwards these requests to the User Profile API Handler (DF10), which validates the authenticated session before querying or updating the database (DF11, DF12) and returning results to the user (DF13).

Data Movement. Data flows are sequential and request-driven. Password reset data flows from the user through the frontend to the Account Management Service and database, with tokens flowing outward through the external channel. Profile data flows from the user through the frontend to the User Profile API Handler and database, with responses flowing in the reverse direction. There are no asynchronous or background data flows described in the scenario.

Trust Assumptions. The architecture defines four trust boundaries. TB1 separates the untrusted external browser from the internal backend services — all user-supplied data crosses this boundary. TB2 separates the token generation and validation processes, ensuring that tokens cannot be validated without passing through the intended verification workflow. TB3 separates authenticated API requests from backend authorization logic, recognizing that authentication and authorization are distinct trust concerns. TB4 separates the active backend processing components from the passive persistent database, reflecting the different trust contexts of processing logic and data at rest. The architecture implicitly assumes that the server-side components operate within a single internal trust zone — no internal boundaries between the Account Management Service, Password Reset Token Module, and User Profile API Handler are described.

9. DFD Explanation

9.1 Processes

The DFD contains four processes corresponding to the four active components. The Web Frontend Interface is the entry process, responsible for collecting user input (password reset requests, token submissions, and profile API requests) and relaying them to the appropriate backend services. It performs no validation or security-critical logic independently — it is a pass-through presentation layer. The Account Management Service is the central orchestration process for the password reset workflow: it receives forwarded requests, verifies user accounts, coordinates token generation, and processes token validation and password updates. The Password Reset Token Module is a specialized process that handles only token generation and validation — it receives requests and returns results. The User Profile API Handler is the central process for the profile management workflow: it receives authenticated API requests, validates sessions, and queries or updates profile data.

9.2 Data Flows

DF1 represents the user's submission of a password reset request through the frontend — this is the starting point of the reset workflow. DF2 carries the same request from the frontend to the Account Management Service. DF3 represents the service's verification query against the database. DF4 is a bidirectional flow between the Account Management Service and the Token Module for token generation. DF5 delivers the generated token to the user through an external communication channel — this is the only data flow that traverses an external system not directly controlled by the application. DF6 represents the user's submission of the reset token and new password. DF7 forwards this submission to the Account Management Service. DF8 represents the token validation and password update against the database.

DF9 represents the authenticated user's submission of a profile API request. DF10 forwards this request to the User Profile API Handler. DF11 represents the profile handler's query or update against the database. DF12 returns the database response. DF13 returns the API response to the user.

9.3 Trust Boundaries

TB1 is crossed by DF1, DF2, DF5, DF6, DF7, DF9, DF10, and DF13 — all data flows between the browser and the internal services cross this boundary, making it the most frequently traversed trust boundary. TB2 is crossed by DF4, isolating the token generation process from the validation process. TB3 is crossed by DF10 and DF13, marking the transition from authenticated API requests to backend authorization logic. TB4 is crossed by DF3, DF8, DF11, and DF12, isolating the database from direct external access — all database interaction is mediated by backend services.

9.4 Architectural Assumptions

The DFD assumes: (a) the Web Frontend Interface is a thin client that forwards requests without independent security logic; (b) the Account Management Service is the sole consumer of the Password Reset Token Module; (c) the Backend User Database is accessed by both the Account Management Service and the User Profile API Handler; (d) the External Communication Channel is a separate delivery mechanism not directly controlled by the application; (e) no intermediate proxies, API gateways, or load balancers are described; (f) user authentication for profile API access is established prior to the API request and is represented as an authenticated session context rather than a separate authentication flow.
