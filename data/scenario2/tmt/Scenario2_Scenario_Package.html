6. Trust Boundaries

Boundary IDComponents SeparatedWhy It Is a Trust BoundarySecurity Significance
TB1 External User Browser ↔ Internal Backend File Processing Service The browser is an externally controlled environment operated by the user; the backend services are internally operated and managed by the system. Data crossing this boundary originates from or is delivered to an untrusted external actor. · All uploaded files cross this boundary (DF1, DF2).
· All download requests cross this boundary (DF6).
· All retrieved files cross this boundary (DF8).
· Any data in transit across TB1 is exposed to interception, modification, or injection by external parties.
TB2 Backend File Validation Logic ↔ Persistent Storage Repository The validation module performs active processing logic (type and size checks); the storage repository is a passive persistence layer. They operate in different trust contexts — validation logic is transient and rule-based, while storage is persistent and holds sensitive data at rest. · Validated files and metadata cross this boundary for storage (DF5).
· File reference identifiers cross this boundary on return (DF7).
· File data crosses from the processing/validation context into the persistent storage context.
· Compromise of this boundary could allow storage of unvalidated content or unauthorized retrieval of stored content.
TB3 User-Controlled Uploaded Content ↔ Server-Side File Handling Components Uploaded files are user-controlled content — their type, size, naming, and internal structure are determined by the user. Server-side components (validation module, storage repository, retrieval handler) process this content based on server-side rules. This boundary represents the transition from untrusted user input to server-side processing logic. · Uploaded file data crosses this boundary from user control to server processing (DF2, DF3).
· The server must treat all user-supplied content as potentially malicious.
· Inadequate handling at this boundary could allow malicious content to bypass validation or exploit processing logic.
TB4 Authenticated File Request Session ↔ File Retrieval Authorization Logic The authenticated session represents the user's identity claim; the retrieval authorization logic determines which files the authenticated user is permitted to access. These are distinct trust contexts — session authentication does not automatically imply authorization for every file. · Download requests cross this boundary when the system must verify whether the authenticated user is authorized to access the requested file (DF6).
· Compromise of this boundary could allow authenticated users to retrieve files they are not authorized to access.
· Separation of authentication from authorization is essential for enforcing per-file access control.

8. Architecture Explanation

The Scenario 2 architecture models a web-based file management application with a three-tier structure: a client-side presentation tier (Web Frontend Interface), a server-side application tier comprising three components (Backend File Processing Service, File Validation Module, and File Retrieval Handler), and a data tier (Server Storage Repository). The system's primary purpose is to allow authenticated users to upload files and retrieve them later through download requests.

Component Interactions. The system supports two primary workflows — upload and download — both initiated by the authenticated user through the Web Frontend Interface. During upload, the user submits a file (DF1) which the frontend forwards to the Backend File Processing Service (DF2). The processing service orchestrates the upload by passing the file to the File Validation Module (DF3), receiving the validation result (DF4), and — if validation succeeds — storing the file and metadata in the Server Storage Repository (DF5). The repository returns a file reference identifier (DF7) which is propagated back to the user. During download, the user submits a request with the file reference identifier (DF6); the File Retrieval Handler locates the file in the repository and returns it (DF8).

Data Movement. Data flows are strictly sequential and request-driven. During upload, file data flows inward from the browser through the frontend, processing service, and validation module, ultimately reaching the storage repository. The file reference identifier flows outward as confirmation. During download, the file reference flows inward, and the retrieved file flows outward. There are no asynchronous or background data flows described in the scenario.

Trust Assumptions. The architecture defines four trust boundaries. TB1 separates the untrusted external browser from the internal backend services — all user-supplied data crosses this boundary. TB2 separates the active validation logic from the passive persistent storage, reflecting the different trust contexts of processing logic and data at rest. TB3 captures the transition from user-controlled content to server-side handling — all uploaded files are user-controlled and must be treated as potentially untrusted. TB4 separates the authenticated session (identity claim) from the retrieval authorization logic (access decision), recognizing that authentication and authorization are distinct trust concerns. The architecture implicitly assumes that the server-side components (Backend File Processing Service, File Validation Module, File Retrieval Handler) operate within a single internal trust zone — no internal boundaries between these server-side components are described.

9. DFD Explanation

9.1 Processes

The DFD contains four processes corresponding to the four active components. The Web Frontend Interface is the entry process, responsible for collecting user input (file uploads and download requests) and relaying them to backend services. It performs no validation or security-critical logic independently — it is a pass-through presentation layer. The Backend File Processing Service is the central orchestration process for the upload workflow: it receives forwarded files, invokes validation, and coordinates storage. The File Validation Module is a specialized process that performs only file type and size checks — it receives file data and returns a pass/fail result. The File Retrieval Handler is the central process for the download workflow: it receives download requests, locates files in the storage repository, and returns them to the user.

9.2 Data Flows

DF1 represents the user's submission of a file through the upload form — this is the starting point of the upload workflow. DF2 carries the same file data from the frontend to the backend processing service — the data is unchanged; only the transport context shifts. DF3 passes the file to the validation module for type and size checking. DF4 returns the validation result. DF5 stores the validated file and metadata in the repository. DF7 returns the file reference identifier from storage to the backend service. DF6 represents the download request — the user submits a file reference identifier through the frontend. DF8 returns the retrieved file to the user.

9.3 Trust Boundaries

TB1 is crossed by DF1, DF2, DF6, and DF8 — every data flow between the browser and the internal services crosses this boundary, making it the most frequently traversed trust boundary. TB2 is crossed by DF5 (file storage) and DF7 (reference identifier return), isolating the storage repository from direct external access. TB3 is crossed by DF2 and DF3, marking the transition from user-controlled content to server-side processing. TB4 is crossed by DF6, where the authenticated session is evaluated against the retrieval authorization logic.

9.4 Architectural Assumptions

The DFD assumes: (a) the Web Frontend Interface is a thin client that forwards requests without independent security logic; (b) the Backend File Processing Service is the sole writer to the Server Storage Repository for upload operations; (c) the File Retrieval Handler is the sole reader for download operations; (d) the File Validation Module interacts only with the Backend File Processing Service; (e) no intermediate proxies, content delivery networks, or API gateways are described; (f) user authentication is established prior to file operations and is represented as an authenticated session context rather than a separate authentication flow.
