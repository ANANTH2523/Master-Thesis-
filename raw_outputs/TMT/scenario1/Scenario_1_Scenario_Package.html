Deliverable 7 — Trust Boundaries

Boundary IDComponents SeparatedWhy It Is a Trust BoundarySecurity Significance
TB1 External User Browser ↔ Web Frontend Interface / Authentication Server The browser is an untrusted, externally controlled environment. The frontend and authentication server are internally operated components. · Session tokens are returned across this boundary (DF5).
· Authenticated requests cross this boundary (DF6).
· Any data in transit across TB1 is exposed to interception, modification, or replay by external parties.
TB2 Authentication Server ↔ Backend User Database The authentication server is a processing component; the database is a storage component. They operate in different trust contexts — the server handles real-time logic while the database holds persistent, sensitive records. · New account records are written across this boundary (DF3 during registration).
· Compromise of this boundary could expose all stored credentials or allow unauthorized record modification.
TB3 Browser Session Storage ↔ Server-Side Session Validation The session token is stored in the browser (an untrusted environment) but is relied upon by the server-side Session Management Module for authorization decisions. The trust boundary exists because the token's integrity and confidentiality cannot be guaranteed once it leaves the server. · Session tokens are stored client-side (DF5) and presented server-side (DF6 → DF4).
· Any party with access to the browser's session storage can obtain the token.
· Token tampering, theft, or replay across this boundary directly enables unauthorized dashboard access.

Deliverable 8 — Architecture Explanation

The Scenario 1 architecture models a web-based user authentication system with a classic three-tier structure: a client-side presentation tier (Web Frontend Interface), a server-side application tier (Authentication Server and Session Management Module), and a data tier (Backend User Database). The system's primary purpose is to allow users to register accounts, authenticate via username and password, and access a protected dashboard upon successful login.

Component interactions follow a linear request–response pattern. The End User, acting through a browser, submits credentials (registration or login) to the Web Frontend Interface (DF1). The frontend does not perform credential validation itself; it forwards the request to the Authentication Server (DF2). The Authentication Server is the central orchestrator: it queries the Backend User Database to validate credentials (DF3) and, upon successful validation, coordinates with the Session Management Module to generate a session token (DF4). The token and the authentication result are returned to the frontend (DF5), which stores the token in the browser's session storage. On subsequent requests for the protected dashboard, the browser attaches the session token (DF6), which is ultimately validated by the Session Management Module (via DF4) before access is granted.

Data movement is strictly sequential and request-driven. No asynchronous or background data flows are described. Credentials flow inward from the browser to the database; session tokens flow outward from the server to the browser; and authenticated requests flow inward again, carrying the token for verification. The architecture does not describe any caching, load balancing, or intermediary layers.

Trust assumptions are captured by three trust boundaries. TB1 separates the untrusted external browser from the trusted internal infrastructure. TB2 separates the authentication processing layer from the persistent data store, reflecting the different trust contexts of real-time logic and data at rest. TB3 captures the fundamental tension between client-side token storage (untrusted) and server-side token validation (trusted). The architecture implicitly assumes that the internal components (Authentication Server, Session Management Module, Backend User Database) operate within a single trust zone — no internal boundaries between these server-side components are described in the scenario.

Deliverable 9 — Data Flow Diagram Explanation

9.1 Processes

The DFD contains four processes corresponding to the four architectural components. The Web Frontend Interface is the entry process, responsible for collecting user input and relaying it downstream. It performs no security-critical logic itself — it is a pass-through presentation layer. The Authentication Server is the central decision process: it receives credential requests (DF2), queries the database (DF3), requests token generation (DF4), and returns results (DF5). The Session Management Module is a specialized process handling only session token lifecycle — generation, storage of session state, and validation. The Backend User Database is modelled as a data store rather than a process, as the scenario describes it as a passive storage component that responds to queries from the Authentication Server.

9.2 Data Flows

DF1 represents the user's submission of credentials through the browser. This is the starting point of both the registration and login workflows. DF2 carries the same credential data from the frontend to the Authentication Server — the data is unchanged; only the transport context shifts from client-side to server-side. DF3 represents the Authentication Server's query against the Backend User Database: during registration this is a write operation (storing new credentials); during login this is a read operation (validating existing credentials). DF4 is a bidirectional flow between the Authentication Server and the Session Management Module. On successful login, the server sends a token generation request; the module returns the generated token. On subsequent requests, the server sends the token for validation and receives a validation result. DF5 carries the authentication result (and, on success, the session token) from the Authentication Server back to the Web Frontend. DF6 represents the authenticated dashboard request: the browser sends a request to the frontend that includes the stored session token.

9.3 Trust Boundaries in the DFD

TB1 is crossed by DF1, DF2, DF5, and DF6. Every data flow between the browser and the server-side components crosses this boundary, making it the most frequently traversed trust boundary in the system. TB2 is crossed only by DF3, isolating the database from direct external access — all database interaction is mediated by the Authentication Server. TB3 is conceptually crossed by DF4 (when validating a token that was stored client-side) and DF6 (when the browser presents the token). This boundary captures the fact that a token originating in an untrusted environment (browser storage) is being relied upon by a trusted process (Session Management Module) for authorization.

9.4 Architectural Assumptions

The DFD makes the following assumptions consistent with the scenario: (a) the Web Frontend Interface is a thin client that forwards requests without independent security logic; (b) the Authentication Server is the sole consumer of the Backend User Database; (c) the Session Management Module interacts only with the Authentication Server, not directly with the frontend or database; (d) no intermediate proxies, load balancers, or API gateways are described; (e) the external communication channel for delivering the session token to the browser (DF5) is the same HTTP channel used for all browser–server communication.

Deliverable 11 — Research Justification

This architecture documentation is sufficient for architecture-level threat modelling without requiring a real software implementation for the following reasons, grounded in established threat modelling methodology (Shostack, 2014; OWASP, 2020; Howard & Lipner, 2006).

First, the scenario provides a complete data flow specification. All six data flows (DF1–DF6) are explicitly described, including their source, destination, data content, and the sequence in which they occur. This is the minimum input required for STRIDE-per-element analysis, which applies threat categories to each element of a Data Flow Diagram (processes, data flows, data stores, and external entities). No implementation detail is needed to determine, for example, that credentials flowing from the browser to the server (DF1, DF2) are susceptible to interception or that the session token (DF5, DF6) is susceptible to theft — these are properties of the data flow architecture, not of any specific technology.

Second, trust boundaries are explicitly defined and architecturally meaningful. The three trust boundaries (TB1, TB2, TB3) represent fundamental transitions in trust context — from untrusted external actor to internal system (TB1), from processing layer to storage layer (TB2), and from client-side token storage to server-side token validation (TB3). These boundaries are inherent to the described architecture and do not depend on specific security controls or technologies. Any implementation of this architecture, regardless of technology stack, would need to address the same trust transitions.

Third, all components, assets, and entry points are explicitly enumerated. The scenario names four components, four assets, and four entry points. Each component has a clearly defined role in the architecture, each asset has an identifiable owner and security relevance, and each entry point is connected to specific data flows. This completeness ensures that STRIDE-per-element analysis can be applied systematically without gap.

Fourth, the architecture is technology-agnostic. The scenario deliberately avoids specifying implementation technologies (e.g., database type, web framework, authentication protocol, encryption method). This is a strength for threat modelling, not a limitation: it ensures that the derived threat model captures architecture-level threats that apply to any implementation, rather than implementation-specific vulnerabilities that might not generalize. The resulting threat model is therefore suitable as a benchmark for comparing different threat modelling tools, each of which may make different technology assumptions.

Fifth, the documentation supports reproducibility. By specifying all architectural elements in a structured format with explicit data flows and trust boundaries, the scenario package enables any analyst — human or AI — to reproduce the same threat model from the same inputs. This reproducibility is essential for the thesis research design, which requires comparing the outputs of multiple threat modelling approaches against a common reference architecture.

In summary, the scenario package provides the four prerequisites for STRIDE-based threat modelling identified by Shostack (2014): (1) a data flow diagram, (2) trust boundaries, (3) processes and data stores, and (4) external entities and entry points. No implementation details are required to identify architecture-level threats; such details would, in fact, reduce the generalisability of the resulting benchmark.
